### explain 核心字段

[TOC]

mysql执行计划输出一张表格，通常包含以下重要字段：

| 字段名            | 核心作用                       | 优化关注点                                                   |
| :---------------- | :----------------------------- | :----------------------------------------------------------- |
| **id**            | 查询中SELECT的标识符或执行顺序 | id值越大越先执行；id相同则从上往下执行                       |
| **select_type**   | SELECT语句的类型               | 区分是简单查询、子查询还是联合查询                           |
| **table**         | 当前行访问的表名               | 也可能是派生表的别名（如 `<derived2>`）                      |
| **partitions**    | 查询会访问哪个分区             | 如果使用了分区表，可确认是否进行了分区裁剪                   |
| **type** ⭐        | **访问类型**，核心性能指标     | 从优到劣：`system` > `const` > `eq_ref` > `ref` > `range` > `index` > `ALL` |
| **possible_keys** | 可能使用的索引                 | 看是否有合适的索引可供选择                                   |
| **key** ⭐         | **实际使用的索引**             | 若为 `NULL`，说明没用到索引，需要优化                        |
| **key_len**       | 实际使用的索引长度             | 判断是否用到了复合索引的**最左前缀**原则                     |
| **ref**           | 索引列与哪个值或列进行比较     | `const` 表示常数，列名表示与另一列关联                       |
| **rows** ⭐        | **估算的需要扫描的行数**       | 数值越大越不好，应尽可能降低这个值                           |
| **filtered**      | 符合查询条件行数的百分比       | `rows` × `filtered` ≈ 实际返回的行数                         |
| **Extra** ⭐       | **附加信息**，包含很多优化线索 | 出现 `Using filesort` 或 `Using temporary` 通常是坏兆头      |

####  `type`：访问类型（性能核心）

这是最重要的性能指标，从优到劣依次是：

- **`system`**：最优，表只有一行（系统表），基本遇不到。
- **`const`**：非常快，通过主键或唯一索引定位到**一行**。如 `WHERE id = 1`。
- **`eq_ref`**：多表连接时，使用主键或唯一索引进行关联，每次只匹配一行。
- **`ref`**：使用非唯一索引前缀匹配，返回**多行**。如 `WHERE name = '张三'`（name 有普通索引）。
- **`range`**：索引范围扫描，`BETWEEN`、`>`、`<`、`IN` 等。
- **`index`**：**索引全扫描**。比全表好一点，但扫描了整个索引树。
- **`ALL`**：**全表扫描**，最差。需要重点优化。

> **优化目标**：至少优化到 `range` 级别，争取达到 `ref` 或 `const`。

#### `Extra`：附加线索

- **`Using filesort`**：需要额外的排序操作，无法利用索引完成 `ORDER BY`。**优化**：为 `ORDER BY` 的字段建立合适的索引。
- **`Using temporary`**：需要使用临时表来保存中间结果，常见于 `GROUP BY`、`DISTINCT`、`UNION`。**优化**：消除临时表，或为分组、去重字段建索引。
- **`Using index`**：**覆盖索引**，非常好。所有需要的数据都在索引中，无需回表。
- **`Using where`**：MySQL 在存储引擎层返回数据后，还需要在服务器层进行过滤。通常没问题，但如果伴随 `ALL` 或 `index` 就需要注意。
- **`Using index condition`**：使用了索引下推优化（MySQL 5.6+），是好事。
- **`Using join buffer`**：关联查询没有使用索引，需要内存缓冲区来辅助。**优化**：为关联字段添加索引。

#### `rows`：估算扫描行数

这个数值是**估算值**，但很有参考意义。扫描 1 万行和扫描 100 行，速度天差地别。

#### `key_len`：索引使用长度

对于复合索引（如 `INDEX(a, b, c)`），通过 `key_len` 可以判断实际用到了索引的哪几列。

- 例如 `key_len = 4`（INT 类型），说明只用了第一列。

- 如果 `key_len = 8`，说明用到了前两列。

- **优化**：如果设计的是复合索引，但实际只用了一部分，可以考虑调整索引列顺序，或查看 SQL 是否破坏了最左前缀。
